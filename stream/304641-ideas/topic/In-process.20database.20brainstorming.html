notramo (Oct 16 2026 at 15:40):

sqlite sucks.
It saddens me that every time I see some cool Roc web or app framework, the storage layer is sqlite. I instantly lose interest in any Roc project where I see SQL, especially in the form of sqlite. Migrations are terrible, it has a dynamic schema, and a huge C library that needs platform support.
And SQL query language is so different, compared to Roc. This is the worst thing. Most of the logic is about conversion between the two paradigms.

SurrealDB is quite good, but it's not supported in any Roc framework, and it's more like a Postgres alternative, not an sqlite alternative. It's much better for web projects than Postgres. I would never use Postgres for anything, if I can use SurrealDB instead. But for simple apps, where basic object persistence is required, a separate database process is overkill.

I think, a new, pure-Roc in-process object persistence framework could be written in about ~6000 lines of Roc code. (Maybe even in ~4000 lines.) It could work with any platform that provides basic file I/O, and it could provide a much more ergonomic query language, i.e. everything that's possible in Roc, because it's pure Roc. And the whole Roc typesystem, (including tag unions and other niceties) could be used for storing data.

Basic feature set that would be useful:

  • Migrations, with mandatory error handling. Roc's error handling is a huge utility for this.
  • Transactions with rollback. I think, Roc immutability can help a lot.
  • Nested data, not just top level fields per record. Two dimensional data is a limitation in SQL.
  • Link constraints (a.k.a. foreign-key constraints in SQL). Also in nested data, see SurrealDB for how it works.
  • Full ACID compliance.
  • Plain Roc query language, no special syntax.
  • Data manipulation should be pure, and syncing to storage is the only effectful thing.

I have some architecture ideas, and I'll write them here soon, but meanwhile if anyone is interested in this, dump ideas here.

Let's design the in-process database for the next generation of Roc apps together!

notramo (Oct 16 2026 at 20:50):

Also I don't know how you would get both strict typing and also avoid migrations.

I want typed migrations with mandatory error handling. For example, most ORMs allow you to write a migration that changes an optional text field to a required one. Then, if the production DB has one record where that field is null, the migration fails. But it should be possible to type this field modification as returning Try({}, [IncompatibleValue]), so it's obvious when writing the migrations that it can fail, and has to be explicitly handled. This is a very simple example, but as the schema gets more complex, there are many more ways to fail, and if it's not tracked in the type system, migrations can quickly become a bad experience.
