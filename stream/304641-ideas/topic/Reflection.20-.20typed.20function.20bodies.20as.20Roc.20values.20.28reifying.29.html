Topic: Reflection - typed function bodies as Roc values (reifying)

Karakatiza (Oct 19 2026 at 12:18):

I have been working on a version of this for a while - in the form of reification - representing the function body as value.

The design: if a function accepts a Code(f) argument, you can pass finto it, where f is a type of any pure Roc function expression. The compiler passes into this argument a Typed AST value that can be translated as necessary within Roc. The function passed can be polymorphic, and the types inside are resolved just like they would in a normal function call site. What you translate the AST into is your business - could be strings for SQL, could be effectful platform calls.

It is beautiful IMO, it unlocks various DSLs that have no syntax overhead - imagine:

  # main.roc: the rows are ordinary records, the clauses ordinary Roc functions
  Product : { id : I64, title : Str, price : Dec }

  products : Sql.Table(Product)
  products = Sql.table("products")

  is_premium : Product -> Bool
  is_premium = |p| p.price >= 20

  expect is_premium({ id: 1, title: "Espresso machine", price: 249 })

  premium : Try(Str, Sql.Error)
  premium = Sql.from(products).filter(is_premium).select(|p| { title: p.title }).to_sql()
  # Ok("SELECT products.title AS title\nFROM products\nWHERE (products.price >= 20.0)")

Notice how transforms and predicates are pure Roc and operate on plain Roc struct, yet the result is domain-specific.

Since there's this discussion, I'll publish the prototype in a couple of days - there are some features I wanted to polish first.

Karakatiza (Oct 19 2026 at 14:54):

The types are inferred based on the usual Roc rules - the question is how these types are translated. The idea is the Translator function preserves the semantics of the type - e.g. uses the correct implementation for integer and float divisions, uses appropriate target types for u32 and u64 Roc values etc. This is a pretty basic expectation IMO - if a translator does not respect Roc types it is malformed. I imagine most translators won't implement all types abd primitives; in this case the translator rejects the AST node, and the user gets a nice error with clear code location

Karakatiza (Oct 19 2026 at 15:03):

To be clear, the code that gets reified is not DSL - it is Roc - the DSL is the function that reifies it. The semantics you express are the Roc semantics, and a well-written DSL (that uses translators that process the AST, resulting from reification) should respect them.

Karakatiza (Oct 19 2026 at 15:35):

It is not a novel idea - there are similar features in C# (System.Linq.Expressions) and Julia (Quoting), and reification is considered a great feature in both.
Often reification has downsides like loss of types or patchy language coverage, but the beauty of Roc's type system allows for strict typing through-and-through and a clean boundary - all pure Roc (whose types can be fully resolved at the call site) being supported for reifying.

Karakatiza (Oct 19 2026 at 18:54):

so Code(is_premium) produces a typed AST in a form similar to

Basically, only the substitution happens when the function expression is passed into a matching Code(a) slot - no explicit Code(value) call - Code stays type-level.
In the example filter has type filter : Query(row), Code(row -> Bool) -> Query(row), where Query is the usual Roc type that hosts the builder pattern methods and "state".

is_premium's Product fits into the polymorphic slot of the Code(row -> Bool) type, so is accepted and reified into the typed AST - every field name, value type etc. is known - resolved as in a simple Roc call.

The AST is not translated "back" to Roc. The "Translator" - the Roc code that received the Code(a) value and matches/processes the recursive AST tag union - builds whatever representation it wants, or, again, does some effectful calls if it needs to, making the return value a Task. There is no mechanism to get the compiled Roc back from the reified value. You can of course call the function you reify in one place normally in a different place - the reification happens at call site of the reifier function (that triggers the reifying because of the Code in it's type declaration), with types resolved there.
