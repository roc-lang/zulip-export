Topic: compiler invariants in release builds

Steve Howell (Nov 04 2026 at 13:14):

Anton asked me to start a discussion from the end of #12748, which Claude found and fixed for me. The bug was a compile-time constant (a record holding an empty list with spare capacity) that reached StaticInitializerMachine.evalLowLevel with an op it didn't expect. A debug compiler panics there with a clear message ("non-construction low-level operation reached static initializer materialization"). The release compiler doesn't, because base.invariant is unreachable in optimized builds, as design.md specifies. So the nightly quietly emitted a list pointing into read-only memory, and the user's roc test died with a SIGSEGV that looked like a bug in their own program.

The invariant policy is sound in general: no runtime checks in hot paths, no fallbacks, no silent repair. But on cold paths like the static initializer, which run once per constant at compile time, keeping the check would cost essentially nothing. It would also turn a mysterious segfault into "compiler bug: (invariant), please report", which is the most useful bug report we could get from users of the nightlies. That wouldn't be a fallback or a repair. It's still a crash, just a loud one with a message.

So the question is whether it's worth having a second kind of invariant that stays checked in release builds, for compile-time paths where performance doesn't matter, or perhaps shipping the nightlies with safety on. Or is there a reason the unreachable matters even there that I'm missing?
