Richard Feldman (Oct 18 2026 at 16:34):

sure! so here are some of the downsides I've seen in "expose a representation of the type as a value" in other languages:

  • if I can ask "get the representation of this type" of any type, and then programmatically get values from it (e.g. I can say "I see that this is a record with a field named foo whose type is Str, and also I can use that type info to access the value of that foo field at runtime), that means that module boundaries are no longer strictly enforced like they are today, because there's a workaround you can use to read the "private" data from any value anywhere.
    • That in turn means any package that does effectful functions involving network requests can now be used to exfiltrate any secret in the program, whereas today they need to be passed those secrets explicitly.
    • This is not a downside in Zig because Zig doesn't have opaque data types by design
    • This could be mitigated by having a rule like "you can only get the type info of a type whose internals you can access from here," but then that has to be reflected in the type system somehow; otherwise the compiler couldn't infer a type for the lambda |a| typeinfo a without introducing a new type for "a type variable whose typeinfo can be accessed from this scope"
  • Parametricity guarantees disappear; as the most basic example, today, a -> a has only one implementation. if you can get the type info of a as a value, you can make that function return a different value depending on what you pass in.
    • That in turn means you can no longer learn as much from type signatures anymore, e.g. List(a) -> List(a) would not longer tell you as much as it does today.
    • Again, Zig's comptime already doesn't guarantee parametricity, so this is not a downside for Zig.
  • Some compile-time warnings become either impossible or easily defeated, e.g. "this nominal record field is unused" is no longer something we can confidently say if anything asks for that type's info, because they could be doing something with the type info of that field, such that deleting the field would break the program.
    • Again, Zig already doesn't have a lot of "unused" warnings that Roc does, which I believe is mostly because of comptime reflection.

notramo (Oct 18 2026 at 19:08):

what use cases would this enable that we can't do today?

A few:

  • For a pure-Roc object persistence framework, it would allow nicer, readable schema/migration syntax and boilerplate-free code.
  • A SurrealDB client, similar to Niclas' roc-pg. However, SurrealDB has a much more powerful data model, e.g. it supports type unions in the database (but it's not tagged, so it can not use the the official encoder API), and returns nested data in CBOR, compared to the row+column output of Postgres.
  • Schema validation libraries (like Valibot/Zod), with more ergonomic syntax and comptime guarantees.
  • The ones I wrote in the issue.
  • Powerful comptime-checked templates.

There are much more, but since it's not currently possible, I instantly discard any idea that could be done with it.

Some more brainstorming, just a dump of probably bad ideas (but possibly some inspiration to someone). Some are use cases, some are possible solutions:

  • I would like a struct builder where the name of the field is available to the function. However, this would only solve some of the limitations, and it would add another limited API.

Here's an example that's not possible currently in a clean way.

This is a coarse concept for an object persistence library:

Post := {
    title: Str,
    content: Str,
}

User := {
    username: Str,
    # Incorrect, should be List(RecordId(Post))
    posts: List(Post),
}

Database := PersistenceEngine({
    users: User,
    posts: Post,
})

If a type has a table, it MUST be linked from other records via RecordId(type), and it's not possible to store the data inline. (Any other supported type is inlined.) Comptime checking would instruct the user to change it to a RecordId(Post) in the above example.

Reflection could convert an arbitrary record into a Dict or List of field/value.

This would help the HTML DSL use case. For example in Joy :
https://github.com/niclas-ahden/joy-todomvc/blob/main/app.roc#L156

header(
        [class("header")],
        [
            h1([], [text("todos")]),
            input([
                class("new-todo"),
                placeholder("What needs to be done?"),
                value(model.draft),
                on_input(|s| UserTypedDraft(s)),
            ]),
        ],
    )

could become

header(
        { class: "header" },
        [
            h1({}, [text("todos")]),
            input({
                class: "new-todo",
                placeholder: "What needs to be done?",
                value: model.draft,
                on_input: |s| UserTypedDraft(s),
            }),
        ],
    )

which is closer to HTML and would avoid a bunch of user imports (class(), placeholder(), value(), on_input() which are here to normalize the attribute types) while remaining type checked.
