What's a linear type? See https://en.wikipedia.org/wiki/Substructural_type_system for more details. A linear type is a type whose values can only be used exactly once.

Steve Howell (Nov 22 2026 at 19:22):

When would one use them? You can use linear types to more easily write robust code. Quoting from wikipedia above: [Linear types] allow the system to safely allocate an object after its use, or to design software interfaces that guarantee a resource cannot be used once it has been closed or transitioned to a different state.

They can also prevent performance issues from mistakenly using the same values multiple times. This is particularly interesting in Roc, as it ties to the behavior where the compiler mutates objects in place under the hood.

# With a linear type (made-up syntax): revoking hands back a
# value that must be used exactly once, and the only thing
# that can use it is ending the streams.
DeviceKeys.revoke_all! : UserId => linear OpenStreams
UserStreams.end_every_stream! : linear OpenStreams => {}

sign_out_others! = |user|
    streams = DeviceKeys.revoke_all!(user)
    Ok({})  # compile error: `streams` is never used

Steve Howell (Nov 22 2026 at 22:44):

One quick update is that the Idris docs are better than anything from above: https://docs.idris-lang.org/en/latest/reference/uniqueness-types.html

Uniqueness Types are an experimental feature available from Idris 0.9.15. A value with a unique type is guaranteed to have at most one reference to it at run-time, which means that it can safely be updated in-place, reducing the need for memory allocation and garbage collection.

Richard Feldman (Nov 23 2026 at 15:53):

so the broad strokes problem is:

  • let's say I write a function that says "you have to give me a unique Foo, and if it's not unique, I get a compile error rather than silent runtime cloning"
  • now we need a formal way in the type system to say "this is not just a Foo, but a Unique Foo" which follows the type around
  • to enforce this, we have to have a concept of "references" which make something be not unique anymore - e.g. I return (foo, foo) in a tuple - now there are 2 references, so foo isn't unique anymore
  • also, passing something to a function may sometimes affect uniqueness and other times not. for example, if I pass a Unique Foo to a function of the type Foo -> Bar, is Foo still unique? It depends. If Bar contains a Foo, and the function stores the given Foo inside the Bar, then Foo is no longer unique. but maybe the function just looks at the Foo and doesn't put it in Bar at all. So we need some way of typing the function to say "I accept Foo but don't affect its uniqueness."
  • the solution to all of these problems means you end up with approximately Rust's type system

Richard Feldman (Nov 23 2026 at 15:55):

I'm oversimplifying a bit there, but basically the reason Rust's type system looks and works the way it does is that if you want to say "I can verify at compile-time that this value is unique," either you need a very restrictive memory model (e.g. Goose) or else you need approximately the same amount of type-system complexity and annotation verbosity as Rust
