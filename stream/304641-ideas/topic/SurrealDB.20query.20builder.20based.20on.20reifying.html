Karakatiza (Oct 31 2026 at 15:46):

The issue is with basic-webserver's design.
Claude:

  1. Every read gives up after 30 seconds. The limit is hard-coded (src/tcp.rs:22). On a quiet live query, the read fails with TimedOut and the app has to reconnect. Bytes from a partly finished read may be lost; the subagent inferred this rather than verified it.
  2. Waiting for data ties up a worker. A read holds one of the 32 Roc worker slots until bytes arrive (src/tcp.rs:357-386, Sleep.roc:3-6). Waiting for pushed messages inside a request handler uses up a slot for as long as it waits.
  3. Nothing runs unless a request comes in. The app's only entry points are init!, respond! and shutdown! (main.roc:11-15). No background loop can keep reading the socket between requests.
  4. Only one user of the connection at a time. A second read or write on the same stream returns StreamBusy (src/tcp.rs:362-380). A handler parked on a read would block every other handler that wants to send an RPC.
  5. App state cannot change. Context is read-only startup data (design.md:144). There is nowhere to keep half-received frames, the table of pending request ids, or the state of live subscriptions.

Karakatiza (Oct 31 2026 at 15:48):

I work on a cloudflare workers platform that supports websocket, but you need to want to design your app around the workers' limitations
