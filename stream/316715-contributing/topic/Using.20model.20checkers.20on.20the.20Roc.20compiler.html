roc-fuzz is a Roc platform for testing pure Roc code past the examples you
write. Fuzz targets check properties over typed inputs with coverage-guided
search; goals, trace rules and allocation measurements check what a passing
campaign exercised; Model searches and fuzzes a stateful component described
as a state machine; and Solve proves or refutes claims about fixed-width
integer arithmetic. Each target builds into one self-contained executable that
checks declared examples, explores, and keeps findings for inspection, replay,
retention and minimization.

Steve Howell (Nov 25 2026 at 21:00):

My roc-markdown processor has a pretty interesting chain of proof. The first version was golang, and it was in the first generation of my chat program. My friend and I, who both worked for Zulip, used the golang dialect of markdown for a couple months and found no surprising behavior. The golang version did NOT have a hand-written parser; it just extended the best golang tool out there. Then I ported the markdown processor to zig with a complete handwritten parser from Claude. We used gold files based on a corpus of about 10,000 real messages from our chat (tuples of markdown and HTML). And then I ported it again to Roc, still using the original 10,000 real-world tuples. And then I eventually retired the corpus in favor of all the other correctness tests. Also, along the whole chain, we were pinning our compliance with a third-party CommonMark corpus. We had deliberate places where we violated the spec, but we never allow the code to regress from matching all the gold files where we agreed on the behavior.

Ulf Bissbort (Nov 26 2026 at 01:02):

A lot of the methods sit at the interface of two existing fields:
a) formal methods is a decades old field in academia where the goal is to specify precisely what a system should do and then prove (or at least exhaustively check) that it does. This ranges from full correctness proofs in Lean/Rocq/Isabelle (seL4,CompCert) to the more lightweight side with model checkers like TLA+ and Alloy, which check a model of your design rather than the code itself.
b) software testing, which has traditionally been much more pragmatic and industry driven: you run the actual code and compare what it does against some oracle. Property based testing, fuzzing, differential testing against an independent implementation (Steve's gold files) and Jepsen style testing, where you record a history of events from the outside and check it against a consistency model, all fall into this bucket.
