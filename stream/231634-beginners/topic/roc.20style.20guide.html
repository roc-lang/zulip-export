Some tips for state machines:

  • State machines MUST be an opaque type.
  • A tag union that describes effects or state changes, MUST use verbs as tag e.g. instead of InsertMode(...) (describes what state is it) use SwitchToInsert(...) (describe what to do).

notramo (Oct 28 2026 at 22:43):

I noticed that certain cheaper LLMs tend to underuse the pipe operator and methods, and nest the function calls instead. Add this:

  • Try to reduce the number of nested calls.
    • Method calls are the best.
    • Pipe operator |> is second.
    • If none of the above fits, nesting remains as a third option.

notramo (Oct 28 2026 at 22:44):

Some more:

notramo (Oct 28 2026 at 22:44):

  • Vague container words are a smell. Entry, Item, Node, Data and Info usually stand in for a word the domain already has, or can be described in a more accurate word.

notramo (Oct 28 2026 at 22:47):

  • Do not use optionals.
    For example, a parser.peek() should not return [Some(Str), None], but [Grapheme(Str), Eof].
    The Some doesn't say anything about what is in that Str, but a Grapheme says it.
    The None just specifies the lack of a value, Eof provides more info by also indicating the reason.
    See a more detailed explanation with examples: https://www.roc-lang.org/faq#option-type

notramo (Oct 28 2026 at 22:49):

  • Reduce what a reader must remember to understand the code. Ask yourself: how many other definitions someone must read to know what a line does? Every jump to a helper, every hidden assumption, and every parameter that never varies adds to that count. A good name helps in this: the reader can figure out the behavior, or helps them remember it. With a bad name, the reader has to remember the implementation too, and also the exact name, since it's not obvious from the name. A rule of thumb: if a helper is used in one place and it's less than 3-4 ines of code, it probably should be inlined. If it largely depends on behavior elsewhere, it probably should be inlined instead.

notramo (Oct 28 2026 at 22:52):

  • Local reasoning over fragmentation. A function boundary must earn its existence by naming a genuine domain concept, isolating platform fiddliness, or eliminating substantial repetition. Do not fracture a 10-line coherent linear flow into five 2-line helpers just because you can. Every helper introduces a name to remember and a call to jump to. And also ambiguity: most names don't accurately describe every behavior. If documenting the behavior would require more text than the function body, it's probably a bad idea to split it. If it's just repacking the error tags with different names, it's probably a bad idea.

notramo (Oct 28 2026 at 22:56):

  • Do not define a shared error type. It's not Rust.
    Roc can infer the error tag union using the _ type variable: Try(..., _).
    Let the compiler infer the actually returned errors. Or specify them yourself one by one if you want to keep track of it, and prevent accidentally introducing more error tags than intended. So, no Try(Str, ParserError) but Try(Str, [Eof, UnexpectedChar])
    This is important so the caller don't have to handle all tags in a type, even if the function only returns a subset of those.

notramo (Oct 28 2026 at 22:59):

  • Treat for and while loops as syntax sugar, not a way to structure code.
    Rule of thumb: if only one var $... is needed to implement a loop, it can provide a more concise code than e.g. a .fold(), especially if something is modified conditionally during the fold, so it would reqire adding a tag union for state tracking. Reduce the cognitive complexity of the code. An extra tag union, an extra variable (e.g. fold state) all add to the complexity.

notramo (Oct 28 2026 at 23:01):

Extend this rule:

  • Use a nominal type (:=) where values of the same shape mean different things. A name passed where an id belongs is then a type error (types).

I would add this sentence:

This is known as the "newtype pattern" in Rust, and Roc has excellent support for it.

notramo (Oct 28 2026 at 23:07):

  • Name functions from the callee's perspective, not the caller's. I.e. name after what it does and not what it's used for. A tokenizer function checking if text starts with a letter should be has_alphanumeric_at(cursor), not starts_identifier(cursor). The caller knows the purpose: is checking the start of an identifier; the function only knows what it does: if an alphanumeric char is at the cursor.

notramo (Oct 28 2026 at 23:19):

Inline a helper that is used once and is under 3–4 lines, or that mostly depends on behaviour defined elsewhere.

I think most LLMs will get confused by this shorter definition. It's not always valid. It's a rule of thumb, not a hard rule. Just to make the bias a bit weaker, not to completely disable. It's mostly a workaround for weaker LLMs. An LLM that would not do it by default just gets confused by this, so I would recommend adding the longer explanation.

Use := where values of the same shape mean different things, so passing a name where an id belongs is a type error.

If you want it concise, simply add this to the end: (a.k.a. "newtype" pattern in Rust).
The "newtype" word probably would activate some Rust-related weights, that would benefit from the usage examples in the vast Rust training data, to help in deciding when to use it.

notramo (Oct 28 2026 at 23:22):

Some more rules:

  • If something is transformed multiple times, and method chaining/piping does not fit the use case, use a var $… instead of numbering, e.g. var $prng instead of prng0, prng1, prng2. A variable assignment overwrites the old value, so it can not be accidentally reused later. You can even declare variables in lambda parameter lists: |var $prng| ....

Steve Howell (Oct 30 2026 at 12:43):

My style guide addresses the pitfall that Str, Str, Str -> Str doesn't give you enough semantic info with the following rule (and some other rules are also kinda relevant):

Neighbouring arguments of one type get a record, even when there are only two of them: they can be swapped and still type-check, and a record names the fields, so order can't go wrong: appended!(conv, who, draft), not four Strs in a row (records).
