Topic: Friction with `WINCH` signal handling in `basic-cli`

notramo (Nov 28 2026 at 14:46):

Currently, when the terminal is resized and the program is subscribed to the WINCH event, a resize cancels what the program is doing.

Start a long running HTTP request, or a subprocess, and it gets canceled because the resize. All I want is to know the new size of the terminal, not to stop what the program is doing. Or not even know the size of the terminal, only that a resize happened, so the terminal will have to be checked some time later.

In Zig or Crystal (and probably in Rust and Go and many other languages), it's approximately 3 minutes to write the necessary code by hand.
In Roc, I gave up after an hour of discussing different possible workaround hacks with an LLM.

This kind of friction is what causes most developers to pick another language.
In Roc, hard tasks are easy, and trivial tasks are impossible.

notramo (Nov 28 2026 at 15:21):

I was thinking about a possible solution, that enables the necessary flexibility, similar to other languages while still preserving the Roc paradigms.

The platform would require a signal_handler! function.

When a signal comes in, don't do anything with the main thread yet. Run the signal_handler! on another thread.

signal_handler! returns a struct with two fields:

SignalHandlerReturn := {
    ## `CustomResult` is a user-specified type.
    ## The content of this field is stored in the platform.
    result: CustomResult,

    ## `Interrupt` causes an `Interrupted` error on the main thread (current behavior).
    ## `Continue` does not disturb the main thread.
    action: [Interrupt, Continue]
}

The CustomResult is different in every app. In most apps it carries something like this:

CustomResult := {
    event: [Resize(TerminalSize), Interrupt, Usr1]
}

TerminalSize := {
    cols: U16,
    lines: U16,
}

This can be used to run custom logic to decide what happens:

  • There are multiple ways to query the terminal size: ANSI codes or an ioctl call.
  • Some programs might want to complete the current rendering cycle before handling an interrupt event.
  • Some programs need to cancel on certain signals, while simply queue the other signals, e.g. until the next render cycle.

Then Signal.get_result! can be used to access the result field in the struct returned by signal_handler!. Maybe repurpose Signal.poll!?

We could do a watch! : List(Request) => Try({}, [SignalErr(IOErr)]) which would allow you to register a specific event so it does not cancel anything. It would make Stdin reads and sleeps return Interrupted and on interrupt you can use poll! to check for the event, so:

Signal.watch!([WindowResize(unix)])?
Signal.catch!([Interrupt])?

response = Http.send!(request)?

match Stdin.bytes!() {
    Ok(bytes) => handle_input!(bytes)
    Err(Interrupted) =>
        if Signal.poll!().contains(WindowResize) {
            redraw!()
        } else {
            cleanup_and_exit!()
        }
    Err(other) => Err(other)
}

Steve Howell (Nov 28 2026 at 16:05):

It would be nice if there was some synergy here for browser apps, because it's often useful to have a browser alternative for native apps, and we solve similar problems. Treat this as would-be-nice request, not a blocker, for me. The API is from Claude:

roc
app [init, step, view] { pf: platform "canvas" }

## What the screen is right now. A terminal host fills the same record
## in character cells; a canvas host in CSS pixels plus the pixel ratio.
Viewport : { width : U32, height : U32, scale : F32 }

## Everything that happened since the last step, in order. Nothing interrupts.
Event : [
    Resize(Viewport),
    Key({ key : Str, down : Bool, mods : Mods }),
    Pointer({ x : F32, y : F32, buttons : U8, phase : [Down, Move, Up] }),
    Wheel({ dx : F32, dy : F32 }),
    Focus(Bool),
    Visibility([Shown, Hidden]),
    Replied({ id : U32, answer : Reply }),   # the answer to an earlier Request
]

Frame : { now_ms : F64, dt_ms : F64, viewport : Viewport, events : List(Event) }

## Work the app wants done outside: it answers later as a Replied event.
Request : [
    Fetch({ id : U32, url : Str }),
    Store({ key : Str, bytes : List(U8) }),
    Load({ id : U32, key : Str }),
    Sound({ name : Str }),
    Title(Str),
]

init : Viewport -> Model
step : Model, Frame -> { model : Model, requests : List(Request) }
view : Model, Viewport -> List(Shape)
