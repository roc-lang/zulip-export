Jonathan (Oct 01 2026 at 14:01):

Say I have a function that matches on a tag union. One tag is reinterpreted but the rest are passed through using a catchall. Should the catchall's union type have the matched tag subtracted?

The case I have right now is an sql query, where NoRowsReturned is reinterpreted a different error (SubsetNotFound) and the rest are wrapped:

match q.query!(query, [{ name: ":name", value: String(name) }], decoder) {
    Ok(count) => Ok(count)
    Err(NoRowsReturned) => Err(SubsetNotFound)
    Err(otherwise) => Err(QueryError(otherwise))
}

The problem is that otherwise still has the tag included in its type ([NoRowsReturned, NoSuchField, ...]) and so the type signature becomes Try(U64, [SubsetNotFound, QueryError([NoRowsReturned, ...])]), even though NoRowsReturned cannot appear in QueryError.

If I manually annotate the function to say that NoRowsReturned cannot happen, it is an error:
This definition can produce the tag NoRowsReturned but the annotated tag union does not list it.

The only solution I have currently is to match on all the other possible error tags to re-return them individually, a bit like we have to do sometimes to re-wrap a Try (unsure if this has changed since polarity). It's not so bad, but I was wondering whether that's likely to stay? (/interested in the reasoning around this kind of feature).

Richard Feldman (Oct 01 2026 at 16:30):

the main challenge here is runtime representation

Richard Feldman (Oct 01 2026 at 16:31):

if I have a tag union of [A, B, C] then at runtime we represent this as an integer where A is 0, B is 1, and C is 2

Richard Feldman (Oct 01 2026 at 16:32):

a tag union of [A, C] will have A being 0 and C being 1 at runtime

Richard Feldman (Oct 01 2026 at 16:33):

so the problem is if you have a match on B which eliminates it, and then another branch that you want to just treat [A, C] as the remaining possibilities, there's more work that has to happen to translate the numbers at runtime

Richard Feldman (Oct 01 2026 at 16:34):

otherwise if the way you reach that branch is because you had C at runtime, that means you had a 2 in memory whereas everything that's working on the [A, C] union only knows how to handle 0 and 1, so you get undefined behavior

Richard Feldman (Oct 01 2026 at 16:34):

a fix could be to automatically do a second match behind the scenes to translate 2 to 1

Richard Feldman (Oct 01 2026 at 16:35):

but it would be nonobvious from the code that a second full conditional is happening, plus I think that was the thing that ran into unexpected implementation problems when someone tried it

Richard Feldman (Oct 01 2026 at 16:39):

so overall my current thinking is that we don't have a good solution here, even though it looks like it should work. Maybe in the future we can find a design that works, but at the moment it's blocked on having an acceptable design.
