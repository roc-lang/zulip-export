Luke Boswell (Nov 20 2026 at 00:13):

I typically isolate most of my logic into modules (or groups of modules under a package) and then I can have multiple application roots use those same modules. So one application root might be using one platform, and another (sitting next to it or in a test/ directory) might be importing those same modules but with another platform.

This is how I structure things so I can use roc-fuzz

Luke Boswell (Nov 20 2026 at 00:42):

In a lot of my platforms, I've been experimenting with a builtin test harness that the host implements and drives the app transparently to simulate effects. I define a custom or simple grammar for test "specs" and the platform host can pick that up and drive the application. The app doesn't know it is being tested and the effects aren't real etc. I can have thousands of e2e behaviour tests driven very fast this way.

Luke Boswell (Nov 20 2026 at 00:43):

So it's not a Roc language level design, but it's been working really nicely.

Luke Boswell (Nov 20 2026 at 00:45):

Here is a spec example from roc-signals -- I guess it's similar conceptually to a playwright style behavior test but built into the platform host.

https://github.com/lukewilliamboswell/roc-signals/blob/main/examples/data-grid/specs/filtering.scm

Luke Boswell (Nov 20 2026 at 00:48):

So my general approach is

  • pure Roc code -> roc-fuzz for asserting properties and invariants
  • e2e behaviour -> platform host test harness through specs

Both of these also provide information about allocations so you can write tests that assert things like this algorithm makes no allocations, or the allocations are flat over time, or the allocations scale linearly with the input etc

Luke Boswell (Nov 20 2026 at 00:57):

Depends on the platform, in roc-signals if you build an app using --target=wasm32 you get a WASM module; if you build using roc build --target=x64musl you get a native test harness that accepts test spec files as a cli argument.

Luke Boswell (Nov 20 2026 at 00:58):

In roc-gui its a little different, we reserve and intercept cli flags for the host. 

roc build my-app.roc

./my-app --host-run-spec specs/greeting.scm

Luke Boswell (Nov 20 2026 at 00:59):

You can either have that be windowless such as in a CI environment without graphics drivers, or get a full-blown script driving an app.

Luke Boswell (Nov 20 2026 at 01:01):

I've even included "screenshot" functionality into the specs which closes the loop so an AI Agent can write throwaway specs to exercise and drive a GUI app and take screen captures of various UI elements all built in. It's so much more efficient and safer than giving access to random tools on my system.
