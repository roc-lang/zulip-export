The list from file_content_bytes_absolute! is fine. The leak is in hostedStdoutWriteBytes in src/stdstreams.zig. Roc passes byte_content to Stdout.write_bytes!, and that hosted function never releases it. The stack trace points at fromSlice only because that's where the leaked block was allocated.

Hosted functions own their refcounted arguments and must release them before returning. The generated roc_platform_abi.zig says this at the top, and also in the doc comment for roc_stdout_write_bytes:

/// Owned arguments. Release each exactly once before returning, ...
///     arg0.decref(roc_host);

Your other stdout/stderr functions already do defer str.decref(roc_host), so this one just needs the same line:

pub fn hostedStdoutWriteBytes(bytes: RocListWith(u8, false)) callconv(.c) StdoutResult {
    const roc_host = g_roc_host.?;
    defer bytes.decref(roc_host);
    ...

You don't need to configure anything on the platform side, and no decref is needed after roc_main. If a hosted function returns or stores an argument instead, it passes ownership on rather than releasing it.

A few other things Claude noticed while reading:

  • The stub functions in dir.zig and both file_create_* functions discard their arguments with _ = str;. They'll leak the same way once a Roc program calls them.
  • hostedCreateAbsoluteBytes takes RocList(RocU8), but RocU8 there is abi.RocU8x16, a 16-byte vector. The generated signature is RocListWith(u8, false).
  • hostedContentAbsolute and hostedContentBytesAbsolute never close the file they open.
