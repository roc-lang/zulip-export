Scott Campbell (Oct 08 2026 at 09:29):

There is the platform API
and there is the underlying host implementation, for each target CpuArch-OS.

So the platform could export a Linux module, and the underlying host implementation does linux things on the linux host... And on a windows host, those could be no-ops or return an error etc.

And then the platform API could return something like: Try(LinuxResult, [CpuArchOSNotSupported]) etc.

Or you can supply a platform per os, with just the relevant API calls, and none of the other irrelevant calls. linux-platform-1.0.0/[hash].tar.zst, windows-platform-1.0.0/[hash].tar.zst etc...

Or you can supply a combined platform API, that supplies the host OS, as a tag union this_host : [Linux, Windows, MacOS] or something, and then app authors can conditionally call the platform APIs.

Just depends on the requirements of the app developers. "I want cross OS support", "I only care about A & B OS...", "I don't care what's under the hood" etc.

So you can either ship extra bloat, or trimmed to just the app developer's use-case.

The point is... that the platform is static, the host ABIs are static C-FFI etc. If you need something dynamic, then you need to dynamically generate a platform at compile time. Or supply a matrix of platforms...

Scott Campbell (Oct 08 2026 at 09:56):

I'm creating godot-roc platform...

And I have multiple versions of godot, godot forks, publish to web -> wasm32-emscripten

The API, will need to support 4.1, ..., 4.7...
And redot (godot-forks from v4.5 ->) 1, 2, 3... 26.

4.7 is backwards compatible with 4.1... but 4.1 is missing APIs that 4.7 has.

Calling 4.7 function on 4.1, could lead to memory corruption etc... these are just function pointers in a table... there is a version api call in 4.1 that i can check the version at runtime (& statically at platform compile time), so I can safely conditionally call the 4.7 apis, comptime & runtime.

I don't have one static platform, instead I'm generating a dynamic one from a pinned version of any given engine(s)...

And from here, I'll need to provide either a all-in-1 platform, or a matrix of platforms... or just the latest platform, with runtime conditionals etc.

So my final workflow looks like...

Godot engine version(s) -> generate platform -> roc glue ...roc abi -> generate matching host implementation

So the roc platform, know which static engine api versions are available, at platform compile time, and can double check at runtime.

And for game devs... they'll just have some-platform/[hash].tar.zst.

I'm still undecided what "some-platform" will be... but for now I'm targeting godot 4.7 API, with the possibility to generate any other combination as needed... so game devs can migrate versions & engines, multi-engine support via runtime conditionals or choose a trimmed down & optimised platform.
