Richard Feldman (Sep 26 2026 at 21:07):

Why do we need both from_quote and from_str? Couldn't we get away with a single function?
Also, why must from_quote return Try(_, [BadQuotedBytes(Str)])? Couldn't it allow any other error?

These are related. I intentionally chose unusual names for the methods that have special meaning to the compiler (e.g. from_quote instead of naming it from_str) because the compiler is only capable of reporting a string error message to the user. If we allowed other errors, the compiler wouldn't know what to do with them; from_quote is hardcoded to only know how to handle that one type of error (and the way it handles it is by displaying the Str inside BadQuotedBytes to the user in the compile-time error message)

Richard Feldman (Sep 26 2026 at 21:07):

so the purpose of keeping them separate in some cases is that from_str can have richer error descriptions than what the compiler supports

Richard Feldman (Sep 26 2026 at 21:09):

also even if your error is just "a Str describing what went wrong" in both from_str and from_quote, you might still want to phrase that string's contents differently depending on whether you expect it to be displayed to a programmer (from_quote) or potentially an end user (from_str)

Richard Feldman (Sep 26 2026 at 21:09):

so in terms of "what does the function do on success," I'd expect from_quote and from_str to commonly work exactly the same way

Richard Feldman (Sep 26 2026 at 21:10):

but I think it's totally reasonable for them to behave differently with regards to how they handle errors, given that one should only be used at compile-time by Roc's compiler, and the other should be used more often at runtime

However, it got me thinking. Consider this code again:

Nothing tells me that the string is actually a Time, I have to look at the advance_time signature. I guess that's true of result as well, but I feel like that's more obvious, whereas it's easy to think that "00:12:58" is just a Str. Maybe that's not a big deal, but I like Zig's philosophy of avoiding magic as much as possible, so I'm wondering whether from_quote(and from_numeral, etc.) are really good ideas.

One might imagine another approach, for example using string prefixes (as exist in Rust, C++, Python, JS, or Swift) such as:

import Time exposing [t_quote]

result = stopwatch.advance_time(t"00:12:58")  # t_quote("00:12:58") called at compile time

This way the conversion is explicit, there's no risk to confuse this with a Str, and the syntax remains convenient and readable.

I know that this ship has probably sailed, but hey we're not quite at 0.1.0 yet, so maybe it's still time to change this?

Aurélien Geron (Sep 26 2026 at 23:57):

Thanks, good to know! However, programmers will often choose the most convenient option, so they'll write"00:12:58" if they're not forced to write "00:12:58".Time. Perhaps the compiler should only allow the "00:12:58".Time syntax.

Basically there's a spectrum from Zig (zero magic) to Ruby (total freedom—magic and monkey patching galore). There's no right or wrong, it depends on what you want to do. Zero magic is awesome for production code, high reliability, team work, ease of maintenance and debugging. Total freedom is awesome for quick scripts and expressive DSLs. My understanding is that Roc wants to find a sweet spot between these two extremes, but it errs much closer to the no-magic side. I feel like from_quote pushes the needle towards magic, and I'm not sure the payoff is worth it.
