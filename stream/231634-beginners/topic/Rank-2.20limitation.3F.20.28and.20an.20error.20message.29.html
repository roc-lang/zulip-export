Richard Feldman (Aug 28 2026 at 16:50):

downsides:

  • it becomes possible to write a method constraint in a new way. I believe that in general, these offer less-nice ways to express your constraints than what's currently available; that is, I think there should always be a way to express a valid constraint more concisely than this, so I don't know why anyone would use this on purpose (as opposed to type inference inferring them because it doesn't know a better way to infer them, and then you can make it nicer with a more concise annotation)
  • in theory it can lead to type constraints accumulating in un-annotated programs in a way that could make performance worse. I am not worried about this in practice, because it has taken this long to find a single example of two constraints on the same method coming up, so I suspect this will be one of those things where in theory it can be slow, but in practice nobody would use it in a way where it would be a problem in practice. (This is especially true because as soon as type annotations are in the mix, this no longer even comes up.)

Richard Feldman (Aug 28 2026 at 16:51):

there's also arguably a "learning curve" downside - but again, I don't think this will come up much in practice, and I wouldn't be surprised if most Roc programmers never even run into this, and are eventually surprised the first time it comes up
