Topic: Temporary solution for concurrency in `basic-cli`?

notramo (Nov 24 2026 at 13:53):

The blocking behavior of basic-cli makes it unsuitable for many projects. Many problems require consuming input from multiple sources at the same time, and immediately reacting when data arrives on any of them.

  • A service manager (like dinit):
    • The control socket (a Unix domain socket), with multiple clients connecting at the same time.
    • The stdout/stderr of each service, for logging.
    • Immediately reacting to e.g. when a service crashes (child process exits).
    • Startup notification fd, or polling scripts.
  • An LLM harness:
    • HTTP SSE or WebSocket streaming to the inference API.
    • Reading user input from stdin.
    • Watching database updates on a TCP socket.
  • An editor:
    • Reading user input from stdin.
    • Reading and writing to the stdio of language plugins.

notramo (Nov 24 2026 at 14:17):

One solution could be to add a worker!, that is exposed to the platform.
It takes a List(U8), because complex objects are too difficult to pass between threads, but a byte slice can be easily cloned fully. The entry point then would deserialize it from CBOR or JSON.

The spawn! platform call would start a worker, and return a worker ID, probably an integer.
The main! would have a worker ID too, probably 1.

Then the platform would manage some messaging. It would be very simple, probably a List(U8), and the destination ID.
send! : WorkerID, List(U8) => () — send a message.
receive! : () => Try((WorkerID, List(U8)), [Empty]) — receive one message from the inbox of the current worker. WorkerID specifies the sender.
receive_blocking! : () => (WorkerID, List(U8))
The receive! and send! functions would be nonblocking, i.e. send! immediately returns (even if the destination worker is not waiting for messages), and the platform buffers it. receive! would immediately return if there's nothing queued.

notramo (Nov 24 2026 at 14:21):

Another solution could be adding a select mechanism. Since most of the problems involve reading from multiple file descriptors at once, maybe this would be simpler.
But in the context of Roc, this may turn out to be more difficult.
How to expose an uniform API for HTTP, UDS, and plain files (stdio, filesystem)?
Ideally, it would not need to run Roc lambdas, because that would be similar to #ideas > Concurrent/threaded platforms, which is known to be very complex. I'm not sure how it could be solved without lambdas.
