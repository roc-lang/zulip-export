Topic: Idea for alternative `parser_for` type signature

Jasper Woudenberg (Aug 02 2026 at 20:46):

Currently a function that performs some parsing (for instance: Json.parse) needs a signature that looks like this:

parse : List(U8) -> Try(a, Error)
    where [a.parser_for : Parser -> (Parser.State -> Try({ value : a, rest : Parser.State }, Error))]

That's quite a mouthful. I wonder if instead it could be this:

parse : List(U8) -> Try(a, Error) where [a.parser_for: Parser(a, Error)]

I don't know if this is possible, and if it is possible what kind of thing Parser would have to be. Maybe a record? Maybe a type alias that defines a bunch of where clauses on its own. If it's possible though, I think there would be many benefits:

  • The type signature of parse functions becomes a lot more intuitive for users of a parsing function, who aren't necessarily interested in the internals of parsing.
  • The Parser type documentation could document all the methods (parse_u8, parse_i8, etc) that need to be implemented for a parser. That's beneficial to authors implementing a new parser.

I'm taking parsing as the example here, but the same can be said for encoding.

What do you think?

Richard Feldman (Aug 02 2026 at 20:55):

we actually have a design for "where aliases"

Richard Feldman (Aug 02 2026 at 21:02):

something like this:

a.Parseable : where [
    a.parser_for : Parser -> (Parser.State -> Try({ value : a, rest : Parser.State }, Error))
]

parse : List(U8) -> Try(a, Error)
    where [a.Parseable]

That's quite a mouthful. I wonder if instead it could be this:

parse : List(U8) -> Try(a, Error) where [a.parser_for: Parser(a, Error)]
