Romain Lepert (Aug 02 2026 at 00:15):

Hi everyone,

I'd like to share with you Terrocotta: a Roc native UI library.
I have been working on it for the past +1month and I think is in a good enough shape to share.

At its core terrocotta is a port of Clay to pure Roc, rendered using roc-ray. It is as faithful to the original implementation as possible and adds some niceties on top: MVU, event bindings, text style inheritance, etc.

The demo examples currently run at 300-600 fps (terrocotta: roc build --opt=speed, roc-ray: zig build -Doptimize=ReleaseFast) but there is probably quite some room for improvement since Clay advertises 10_000 fps.

I hope that it can help the UI effort to some extent. For those interested, I recommend reading the docs/architecture.md for internal explanations.

I also sometimes dump some Roc experience feedback to #24

Romain Lepert (Oct 14 2026 at 19:55):

roc-ray could just as well expose draw commands as data instead of direct draw functions. In both cases the host must make the final GPU call. Unlike model update, rendering is not “pure” conceptually because it has side effects. Also a command list is an allocation with copy and realloc as capacity grows. So I am curious what makes it more adequate to roc’s design in your view ?

pixelsprout (Oct 14 2026 at 20:26):

Yeah, roc-ray could take the same approach, but then it would stop being a faithful port of raylib. Useful software needs side effects, so in Rocco I push them to the edge, where the engine runs them. Drawing has side effects, but describing a frame doesn't, and the Roc side of Rocco stops at the describing part.

Returning a description also pays off on performance. The host interpolates between the last two Scenes, so it never needs to hold an old Model, and the Model stays at a refcount of 1. That lets Roc safely mutate it in place and skip the copies. As for the command list allocating, I measure that in CI: 2 or 3 allocations per step, 0 reallocs, and the host reads the list straight out of Roc memory without copying it.

Keeping step pure gives us replay as well: log the inputs, replay the log, and you end up in exactly the same state. It also means we can test the game without the engine at all, which is great for agents, because they don't need to see the game running to test how it behaves.

Richard Feldman (Oct 14 2026 at 20:47):

Romain Lepert said:

I am curious what makes it more adequate to roc’s design in your view ?

in general, Roc lets you do more with pure functions than you can do with effectful functions - you can run them at compile time, they're easier to test, those tests can never flake, there are caching benefits to tests, etc...

I/O absolutely requires effects, so there's no opportunity to get these benefits there. But rendering not only doesn't require I/O, it's almost always a mistake to do I/O in the middle of rendering

Romain Lepert (Oct 15 2026 at 09:08):

Rocco aims to avoid side-effects by just updating a Model and Scene per game tick

I believe roc-ray also aims to update Model and render it per game tick.

roc-ray update! is currently effectful only to allow certain synchronous effects like window_read_clipboard!, trace_begin!, etc. . It is not a very big difference.

The current main distinction is that roc-ray's render! : Frame, Model -> {} targets effectful draw call while rocco's view : Model -> Scene outputs a list of draw commands for the engine to execute.

pixelsprout said:

Returning a description also pays off on performance. The host interpolates between the last two Scenes, so it never needs to hold an old Model, and the Model stays at a refcount of 1. That lets Roc safely mutate it in place and skip the copies. As for the command list allocating, I measure that in CI: 2 or 3 allocations per step, 0 reallocs, and the host reads the list straight out of Roc memory without copying it.

I don't think the Scene approach is uniquely capable of keeping refcount of 1. roc-ray also keeps refcount 1 because update!() and render!() happen sequentially and render!() releases refcount for next update!() (aka no copies).

Regarding the command list allocating, I am not referring to the host boundary, but rather that view() will be appending draw values to the list continuously. Roc does a 2x geometric capacity growth anytime you exceed the current list capacity. For O(1000) elements which is likely for rich scenes, that is >10 growth, each of which will realloc and may require to move the list in memory : 0 → 2 → 4 → 8 → 16 → 32 → 64 → 128 → 192 → 288 → 432 → 648 → 972 → 1458. Toy CI tests probably won't show that. So code should instantiate List.with_capacity, avoid intermediate command lists and List combinators like map, keep_if.

Richard Feldman said:

in general, Roc lets you do more with pure functions than you can do with effectful functions - you can run them at compile time, they're easier to test, those tests can never flake, there are caching benefits to tests, etc...

I/O absolutely requires effects, so there's no opportunity to get these benefits there. But rendering not only doesn't require I/O, it's almost always a mistake to do I/O in the middle of rendering

  • compile time evaluation: everything but the direct draw calls vs draw command list will be the same amount of purity so i am not sure there would be much of a difference here
  • tests: yes
  • I/O: render! has scoped capabilities so it would reject Files.read_text! for example.

So all in all my read of the two rendering approaches is:

Pros:

  • Testing
  • Scene interpolation
  • Optional draw pipeline layering/reordering etc. (not mentioned but I had thought about it at some point).

Cons:

  • Perf/Allocation management
  • UX

Is that fair ?
