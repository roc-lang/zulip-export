Hi from ZSF!

Just wanted to clarify our perspective a bit and explain how to open an issue to report a bug in a way that will be well-received.

What we care about the most when looking at issues is to make sure that spending time to solve one unblocks Zig users who are trying to use Zig to make software. Zig is still work in progress and lots of things are known to be incomplete or are likely to be rewritten as new features are added or existing ones are polished.

A bug report that affects nobody takes away energy from the main development work and is even likely to be regressed if the relative subsystem will change significantly enough in the future.

For us, a bug report is worth acting on only if it unblocks Zig users and, even then, we're not able to serve all users so some prioritization has to be done (ie some bug reports won't be acted on before we end up overhauling the subsystem, see the new Io interface for example which came in and invalidated many old I/O related issues, while also creating new ones).

If you ever wondered why would we ever not want LLMs to analyze the Zig codebase and report all bugs, that's why. At some point we'll reach a greater level of maturity and we will become increasingly more interested in all bug reports, but right now not only they're not interesting, they would also drown in noise issues that we do want to act on.

So, Roc development makes use of LLMs, and if an LLM tells you about a bug in Zig, then
you can't act on that (as the contribution rules state), how do you unblock yourself then?

It's essentially two steps:

  1. Ensure that the bug is actually there and confirm that it is indeed a blocker for you.
  2. Write an issue to explain your use case and show how to reproduce the bug.

For both steps we ask that you do all the work yourself and don't involve LLMs. This is done to lower the chances of the bug report not being good (i.e. not pointing at a real bug or not being a blocker for you), and to give you the amount of first-hand knowledge necessary to interact on the issue tracker with Zig core contributors, in case that there are follow up questions.

There are also other reasons behind our request to follow this procedure, one for example is that, even if you have complete certainty that your LLM generated report were to always be good, without any form of human authoring, it would still be possible for one project to overwhelm us with by-construction legitimate issues, but we don't want that either.

Additionally, there are some situations where the concept of 'blocker' becomes fuzzy: if you're running a bunch of experiments in parallel, encountering a bug in that setting counts as a blocker? To some degree yes, to some degree no.

These are uncharted waters in software collaboration so I don't know for sure what the best approach would be, but given the set of constraints, my thinking is that it would make sense for the Roc project to have a soft fork of Zig that contains all the trivial fixes that you can have your LLM solve quickly, and reach for the Zig issue tracker for more serious issues, where slowing down and double checking everything is worth your time (e.g. a Zig miscompilation).

You need to be careful to not go too far with your fork (in order to be able to pull easily from upstream), but with some discipline you should be able to get the best of both worlds. Related to this topic, Martin Wickham recently gave a talk at SYCL Vancouver titled Maintaining a Long Term Fork, where he talks about how his previous company used to maintain a long term soft fork of Unreal Engine.

Anyway this is just an idea, hopefully I've made our perspective clear and from there I'm also happy to discuss altrenative approaches if any come to mind. Also at that point we probably should split off a dedicated thread maybe.
