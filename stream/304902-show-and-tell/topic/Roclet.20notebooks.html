Steve Howell said:

Looks great! What do you do use for rendering markdown? (see https://ageron.github.io/roclet/web/edit.html)

Thanks Steve! Roclet uses CodeMirror 6 for the editor, with different highlighting sources:

  • For Markdown we use Lezer's Markdown parser with GitHub-flavored Markdown support (it supplies CodeMirror's highlighting).
  • For Roc we use the Roc compiler directly (running as WASM in a background worker): it provides tokens which are translated to CodeMirror highlighting. Roc code blocks inside Markdown are also highlighted using the Roc compiler.

Aurélien Geron (Nov 02 2026 at 18:11):

notramo said:

Cool project! What prevents the packages to loaded automatically? Why is the manual download and upload needed?

Thanks notramo! Yeah, that's the most annoying limitation of serverless Roclet: it's due to CORS–the browser prevents a script on one website from reading data from a different website—unless that website explicitly grants permission using CORS headers.

The simplest solution is to make the server fetch the packages, but this is not possible on a static website (currently Roclet is hosted on Github Pages = static). For now you can install the Roclet server locally, it solves the problem.

In the short term I can make all the most common packages (including all the ones used in the demos) available on the website, so at least users won't get the download/load experience while trying out Roclet. Or we could provide bundles containing notebooks + package dependencies.

Aurélien Geron (Nov 05 2026 at 03:26):

Thanks everyone for the suggestions! I think a combination of these ideas would work well:

  1. Mirror common packages alongside Roclet, starting with all demo dependencies, including transitive ones. These would be ordinary static files, so trying the demos wouldn't depend on a running backend or its quota.
  2. Use an optional caching download service for other packages, possibly a Cloudflare Worker backed by R2. Packages would download automatically, with compilation and execution staying entirely in the browser.
  3. Keep manual loading as the final fallback, if automatic downloads fail.

Re security, Roclet would keep the original package URLs and verify the content hashes regardless of where the bytes came from. Verified packages are already cached in browser storage.

I also checked the GitHub API suggestion: the API itself supports CORS, but downloading a release asset can redirect to a response without CORS headers. That happened with the roc-time archive I tested, so the API alone doesn't appear to solve it.

Regarding Cloudflare's non-HTML restriction, their docs distinguish ordinary CDN use from products intended for file hosting, such as R2. That looks like a promising route, although I'll check the limits and billing controls before deploying anything.

This should make automatic loading the usual experience, while keeping the demos usable even if the download service hits its limits.
