Niclas Ahden (Oct 18 2026 at 14:05):

This community is so fast, I can't keep up :joy: @Anton's explanation is of course on point!

Roc will figure out the types one way or another: either based on how you use the values, or through explicit type annotations.

It helps to think like this: first Roc does its type-checking, so that it knows all of the types in your program, then it does the compile-time string parsing, and can validate that against your types.

As @Anton mentioned, you could therefore generate code to "materialize" the types of whatever string you're parsing. I'm opting not to do that, because I don't want extra steps. I want it all to "just work" right when you've typed out your SQL query :)

Regarding type annotations: I usually work without types to start and then add type annotations when I want to cement what I've written. In this example I would probably extract a get_planets function and annotate that, so that I have said "I expect this function to return exactly this type of record" as close to the outside world as possible, just like you'd want with an external API or such. That way you get flexibility while experimenting, and then you tighten it up before deploying. This probably isn't news to Roc fans, but perhaps someone new to the community reads this :)

Niclas Ahden (Oct 18 2026 at 14:51):

The errors you see in the video are mostly hand-written by me in the parsing of the string. That's how roc-pg can do "did you mean" based on the SQL schema.

Think of it like this: Roc finishes the type-checking happily and reports no errors. Then it does the comp-time string parsing and I get to decide what errors that can return. In my case I want friendly error messages that help you figure out your SQL issue, which aren't about Roc types at all, really. For the SQL syntax errors I generally just say what Postgres would, to help with familiarity.

So sky's the limit in how good your error messages could be!
